# jawata-studio v3.7.8

Cursor on Windows stops hanging, and the guard finally does its whole job.

Cursor ran jawata's guard as a shell script. On Windows there is no shell to
run it with, so Cursor started one and waited — and because Cursor treats this
particular hook as fail-closed, a guard that never answers does not merely go
quiet, it **blocks the command you typed**. Observed live: a bash window sitting
open on a read that never returns, with the editor waiting behind it.

The guard is now the same native binary already used everywhere else, on every
platform, and existing installs drop the old guard script on their next deploy.

**What this release does NOT do:** Cursor's other three hooks — session start,
prompt submit, and after-tool — are still shell scripts. On Windows they cannot
run, so on that platform Cursor gets the guard and the tools while the memory
and context layer stays silent. It fails quietly rather than blocking, which is
why the visible symptom is gone. Those three are the next port.

Finishing that cutover required finishing the guard. Its binary understood
shell commands but never saw which tool was firing, so it could not stop a
hand-edit of a `.java` file — the case the guard exists for. It now blocks
Edit/Write/MultiEdit on Java sources, honours a `jawata-author:` declaration
for the session that declared it (time-bounded, so it cannot become a standing
bypass), and lets a brand-new file through, since a file that does not exist
yet has nothing to refactor.

Both halves are now pinned by tests that run the real binary rather than the
decision function — the specific gap that let each of the two previous
cutovers ship half a guard.

Also in this release: a redeploy that lands while a hook is executing no longer
fails on Linux's refusal to run a file still being written.
