# v4.0.2 — the verdict is bound to the call that asked for it

**Reading the judge's own instructions was enough to stand a stop down.**

v4.0.0 and v4.0.1 read the verdict from *any* tool result that followed a judge
spawn. The test was `judge_ran` — "a judge was spawned somewhere in this window"
— so every later tool result inherited the judge's authority, including a file
read.

Line-start discipline was the only thing between that and a quotation, and it
does not survive indentation: the reader trims leading whitespace before
matching. The files carrying `VERDICT: RESERVED` indented by four spaces are
exactly the ones an agent has reason to open — the judge's own stance at
`~/.claude/agents/autocontinue.md`, and `docs/release-notes/v4.0.0.md`, which
documents the mechanism.

Measured against the shipped v4.0.1 binary: spawn the judge, let it answer
nothing, read its stance file, and the stop was **allowed**.

## The fix

The verdict now binds to the judge's own `tool_use` id. The transcript carries
`"id"` on the tool call and `"tool_use_id"` on the result — both verified in a
live transcript — and only a result answering one of this window's judge calls
is read.

An id is minted by the harness per call, so it cannot be produced by quoting.
What the agent writes is still rejected, as before; what the agent *reads* is
now rejected too.

A client that omits `id` yields no verdict, and the turn is held until the
empty-turn ceiling releases it. That is the safe direction: holding costs two
pushes, accepting a quoted line costs the whole rule.

## Verified, not assumed

- **Control.** Revert the binding to `judge_ran` and the new case goes red with
  `Some(Reserved)` where `None` is required — the defect reproduced on demand.
- **Artifact.** Against a release build: the attack is HELD, and the judge's own
  indented verdict is still accepted. Both from the same fixture set that
  produced the original finding.

## A probe trap, recorded because it cost real time

A **debug** build of the hook is inert in a scratch harness — it emits nothing,
not even under `JAWATA_HOOK_SELFTEST=1`, while a release build in the same
directory with the same name and payload answers correctly. Timing is not the
cause (both return in 2 ms against a 4 s budget) and the reason is not yet
known.

It does not affect shipped behaviour, because releases ship release builds. It
does mean **any probe of this binary must use a release build** — a debug build
returns silence, and silence from this gate is indistinguishable from "allowed".
Two conclusions during the v4.0.1 dogfood were wrong for exactly that reason
before the release/debug difference was isolated.
