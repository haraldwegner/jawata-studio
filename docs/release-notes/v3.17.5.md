# v3.17.5 — quotes mean mention, and the flag's state follows you into context

**Three changes to the autocontinue mechanism, each from a defect measured live
in the last two days — plus the repair of three interlocks v3.17.4's own first
morning exposed.**

## 1. A quoted "autocontinue" is a mention, not a command

Writing about the word kept switching it on. On 2026-08-31 the message *'Update
the "autocontinue" flag as discussed above'* armed the grant off its **quoted**
mention, and the agent ran a whole morning under permission nobody meant to
give.

Now: the bare word arms; a quoted or backticked word does not. This is not
intent-guessing — five releases failed at that and the ban stands. Quoting is a
syntax you type, and your own messages already separate cleanly along it:
every arming order you've sent is bare, every discussing message quotes.

Details that matter:
- A **stray unbalanced quote removes nothing** — a lone quotation mark cannot
  swallow an order later in the message. That failure would cost a night;
  the chosen failure (an unquoted mention still arms) costs one push.
- **Clearing is untouched.** Any message you type still switches the grant off,
  quoted or not — a mention proves you're present exactly as an order does.
- The end state — `/autocontinue` as a real client command, retiring prose as
  an input channel entirely — is filed in Sprint 28f.

## 2. The flag's state is injected into the agent's context (from v3.17.4-pending)

Your diagnosis: the grant existed twice — the hook's file, cleared when you
type, and the agent's memory of being told, which nothing ever cleared. Now the
hook writes the file's own state into the agent's context on every message:
ON means *work the plan, stop only at its numbered checkpoints*; OFF means *do
what this message asks and stop there*. A background-job wake-up is re-told the
standing state. The line arrives even with the knowledge store down.

## 3. Three interlocks from v3.17.4's first unattended morning

- **One answer froze writing for a whole window.** The answered-flag never
  reset, so the stop gate pushed the agent to work while the write-guard
  refused everything — a deadlock between two fixes that each work alone. The
  gate's own push now resets the flag.
- **Consulting the communicator counted as work**, so a finished session never
  looked idle and could not be released. It no longer resets the emptiness
  counter.
- **The write-guard's refusal claimed "reads are never refused"** while shell
  reads were refused. The text now tells the truth: tool-based reads survive;
  shell commands count as writes, because a commit is one.
