# v3.17.3 — the machine is not you, and an edit is work

**Two things were still ending the autocontinue grant that are not you typing.** Both
are fixed. Two more changes make the next failure diagnosable instead of a
reconstruction from the transcript.

## Why there is a sixth release on one mechanism

v3.17.2 replaced a guess about your words with a rule about a channel: *any message
you type ends the grant, only the word restores it*. The rule was right. The
implementation dropped half of it — it read **"any message"** where you had said
**"keyboard action into the chat window"** — and everything that arrives at that same
hook was treated as you.

That is not a new kind of mistake. It is the same one, at a smaller scale: a
requirement stated precisely, implemented approximately.

## What was wrong

**A background job finishing switched your permission off.** Job-completion notices
and system reminders reach the prompt hook exactly as your typing does. So any run
that started something in the background died at its first wake-up. Measured
2026-08-30: the grant was armed at 11:44:25Z, a job completion cleared it at
11:59:23Z, and the session slept 21 minutes until you came back.

**Only background work counted as having worked.** The gate lets go after two
consecutive turns that did nothing — a wedge-breaker, and correct. But "did
something" was measured as *launched a background job*. A turn that read files,
edited code, ran the compiler and committed counted as **empty**. So an ordinary
working run spent its allowance in two turns and was released, having done nothing
but work. This is why the leash felt short even when the grant was alive.

**The gate recorded nothing about its own decisions.** Six failures on this mechanism,
and every one had to be reconstructed by hand from the session transcript. The 22:54
sleep needed a fresh auditor and a byte-offset dig to reach a single `if`.

**And the activity log named the wrong component's version.** Every line it has ever
written carried the *engine's* version, discovered from a cache directory — not the
version of the binary that wrote the line. On 2026-08-29 it stamped `v3.17.2` onto
lines written hours before that code existed. Together with the missing decision
record, this made *"the fix was wrong"* and *"the fix was not the code that ran"*
indistinguishable — across five failed repairs diagnosed from that log.

## The change

| Event | Effect |
|---|---|
| A message of yours containing **autocontinue** | grant ON, counters reset |
| **Any other message you type** | grant OFF |
| **Esc / interrupt** | grant OFF |
| **A background job finishing, a system reminder** | **no effect** — new |
| Anything the agent writes | no effect |

- The harness check uses the stop gate's own predicate rather than a second copy of
  its prefixes. Two lists nothing forces to agree is how one fix lands in one of them,
  which happened twice in this crate this week.
- When it ignores something as machine text it **says so**, carrying the first
  characters — so if that check ever stops matching, the log names the mismatch
  instead of looking identical to a working guard.
- Work is now *any tool call in the turn*, foreground or background. Editing a file
  resets the counter.
- Every stop decision writes one line: the verdict and the facts it was made on —
  grant state, empty-turn count, whether the turn worked, whether it armed anything,
  whether it had already bounced. **The allow path is recorded too**, and that is the
  half that matters: a gate that logs only its blocks cannot answer *"why did it not
  fire"*, which is the question asked all week.
- Log lines carry this binary's own version, resolved at build time.

## What is NOT changed, and deliberately

**The word still arms the grant wherever it appears in your message**, including when
you are only naming it. That was on the list to "fix" and it is not a defect: every
failure this week was the gate stopping when it should not have. A stray arm costs a
push you can end by typing anything; a stray clear has twice cost a night. It errs in
the cheap direction on purpose.

## Verified

`cargo test -p jawata-hook` — 269 unit tests and every integration suite green.
`cargo build -p jawata-hook` clean, zero warnings.

The harness fix carries its control: a job completion must leave the grant standing
**and** your own typing must still clear it, so a green cannot mean the clear was
simply disabled. The work-counting fix is asserted through the real binary against a
scratch home, reading the log back — not by asserting a function was called.
