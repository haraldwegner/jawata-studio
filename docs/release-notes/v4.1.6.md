# v4.1.6 — the four dev-machine guards become product

On Harald's instruction of 2026-09-08, an hour after v4.1.5. Built from the
v4.1.5 tag, so nothing from Sprint 28e rides along.

## What was wrong

Four guardrails were enforcing rules that are true for every client, on one
Linux machine only. They were written as shell scripts under the user's own
hooks directory — `guard-workspace.sh` (2026-08-21) and `guard-gate-output.sh`
(2026-08-28) — both **two months after** Windows and macOS entered the release
matrix on 2026-06-28.

So they were not leftovers from an early implementation. They were written
after the port, for product-wide problems, and made local. Every other platform
had nothing, and nothing said so: the rule looked handled.

That is the same shape as the cadence rule v4.1.5 shipped, which had also been
offered as a shell script first and refused for the same reason.

## What moved

Four rules, ported faithfully rather than reinvented — each message below is
the one the script had earned incident by incident, and each incident is kept
with it in the source.

**1. Workspace containment.** The agent works inside the declared workspace's
project folders, plus the scratch and agent-config directories. Everything else
in the user's home — sibling projects, private repositories, dotfiles — is
refused. It polices a BOUNDARY, not a spelling: the three home spellings a
shell would expand are expanded first, because until 2026-08-21 only the fully
expanded form was matched and the tilde form of a blocked directory walked
straight past. System paths are never policed; they are toolchain, not user
data.

**2. Git introspection that exposes a credential.** A remote address commonly
embeds a password, and printing one puts it in the transcript permanently. This
caught a real leak on 2026-05-19. Ordinary git is untouched — the rule is about
exposing a remote address, not about git.

**3. An expensive gate must keep its output.** A multi-minute run whose output
is discarded, or truncated through a filter, costs a second run the moment any
detail is wanted. Measured 2026-08-28: two avoidable full runs, roughly twenty
minutes. Reading the FILE afterwards is unrestricted; only producing the output
and throwing it away in one command is refused.

**4. A gate needs an absolute working directory.** A workspace holds several
projects and the shell's directory is not reliably where it was left. Measured
2026-08-28, five times in one session: four failed loudly, and the fifth landed
in a neighbouring repository, ran ITS gate and printed a real PASS about the
wrong product. An absolute script path is caught too — it does not set the
working directory either, and a run invoked that way produced fourteen phantom
failures, every one a fixture resolved from the wrong root.

Rules 1 and 2 police PATHS, so they see the command AND the file a reading or
editing tool is about to touch. A containment rule watching only shell commands
would be satisfied while a file read walked out of the workspace.

## What this release does NOT do

**The paths are hardcoded and Linux-shaped.** `/tmp` is a Unix concept; the
portable form is the platform temp directory, and the agent-config directory
needs the per-client resolution the codebase already has. Windows and macOS
therefore get the RULES and not yet the right paths.

That is filed as its own issue rather than guessed at inside a patch, and the
source says so where a reader meets it. Shipping the rule to the product while
naming the gap is better than leaving all three platforms with nothing, which
is the state this release found.

A fifth local script, `block-security-json.sh`, is deliberately NOT folded: it
hardcodes one credential file in an unrelated project. Generalising it means a
configurable list of secret paths, which is a feature and not a port.

## Verification

`cargo test` over the hook crate: **302 passed, 0 failed**, up from 291 — the
eleven new cases are these four rules', including the two shapes that must NOT
fire (ordinary git, and system paths).
