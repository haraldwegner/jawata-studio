# JAWATA Studio v3.6.1

**Four things found by working v3.6.0 on a Mac.** Three are macOS behaviour;
one changes a default on every platform.

## Closing the window left a dead app

With services running, closing the Studio window kept the app alive — as
intended — but there was then no way back into it. It stayed in the macOS
application switcher, and selecting it did nothing at all: no window, no
response.

macOS tells an app when its icon is clicked while it runs with no window
visible. Studio never listened for that message. The window was hidden and
nothing existed that could bring it back.

It listens now. Clicking the Dock icon, or selecting Studio in the switcher,
brings the window back. So does the tray menu, as before.

## Studio stayed in the application switcher with nothing to show

A service manager with its window closed is doing what the jawata workspaces
themselves do — running in the background. It should not be holding a slot in
the switcher.

Now it does not. With the window closed Studio steps out of the foreground; it
returns the moment the window is opened from the tray or the Dock. A Dock icon
you have pinned is unaffected — that is a shortcut, not the running-app list,
and clicking it still reaches the running Studio.

## The menu-bar icon

v3.6.0 replaced the branded disc with the bare brand mark, on the reasoning
that macOS renders menu-bar icons from their silhouette and tints them. The
reasoning was right and the result was not: measured, that icon was 129 of 1024
pixels of ink in one-to-two-pixel strokes — a hairline, reported as still
invisible.

The right shape for a menu-bar icon is a bold silhouette with the mark cut out
of it. That is what ships now: the disc carries the visibility, the arch is a
knockout in it, and both survive being scaled into the menu bar and tinted.
Coverage went from 12.6% of the icon to about 46%, and a test refuses anything
below a third — a stroke-only icon cannot reach that.

**Still unverified.** As with v3.6.0, this was built and measured but not seen
on a menu bar. The measurements are real; the appearance is not confirmed.

## Updates installed themselves — now they do

Studio checked for new jawata releases, recorded which was newest, and then
waited to be asked. The macOS check found exactly that: Studio knew 3.6.2 was
out while an older runtime kept running, and the update had to be done by hand.

The default is now to install. Checking without installing bought nothing —
putting a downloaded runtime into service is already a separate, deliberate
step. Settings → update policy switches it back to asking, and an existing
settings file keeps whatever it already had.

## Deploy runs are on the record

A deploy's per-client outcome existed only in the window that ran it. Once that
window closed there was no way to find out what a run had done — which mattered
concretely: a client's configuration ended up empty, and the files on disk
could not distinguish "the deploy wrote nothing" from "the deploy wrote entries
and the application overwrote them minutes later".

Every deploy now appends to `logs/deploy.log`: one summary line, then one line
per client with its status, target path, message, which sections changed, where
the backup went, and any validation errors. Skipped clients are recorded too —
a target silently missing from the record is how the previous problem stayed
unreadable.

## Verification

243 tests pass, 0 fail. The deploy log's contents are asserted line by line,
including that a skipped client appears. The menu-bar icon's coverage and its
knockout are asserted numerically.

**What tests cannot show here.** The three macOS behaviours are compiled only
on macOS; this build proves they compile and that Linux and Windows behaviour is
untouched. Whether the window returns on a Dock click, whether Studio leaves the
switcher, and whether the icon is visible all need one pass on a Mac.
