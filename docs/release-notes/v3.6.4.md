# JAWATA Studio v3.6.4

**The installer is notarized now — v3.6.3 only got half of it.**

## What was wrong

v3.6.3 said releases were signed and sent to Apple to be notarized, and that
`accepted` with `source=Notarized Developer ID` was the result that matters.

Checked on a real machine, it was not:

```
jawata-studio_3.6.3_aarch64.dmg: rejected
source=Unnotarized Developer ID
origin=Developer ID Application: Harald Dr. Wegner (AUT4FJ5A5U)
```

The `origin` line shows the certificate was fine — the signing worked. The build
log shows what did not: the **application** was notarized and accepted by Apple,
then the disk image was built from it, signed, and never sent anywhere. Apple's
check of an installer looks at the installer, so the download stayed untrusted
even though the app inside it was not.

That is a bug in this project's release workflow, not in the certificate, the
credentials, or Apple's side. The previous note claimed a result nobody had
measured.

## What changed

The workflow now submits the disk image for notarization as well, waits for
Apple's verdict, and attaches the resulting ticket to the file so the check
works without a network round trip on your machine.

The attach step is also the gate: it cannot succeed unless Apple issued a valid
ticket, so a failed notarization now fails the release build instead of
producing a quietly untrusted download.

Nothing about the application changed. This release is the same code as v3.6.3
with a corrected release pipeline.

## Checking it rather than believing it

On the downloaded file:

```
spctl -a -vvv -t install jawata-studio_3.6.4_aarch64.dmg
```

`accepted` with `source=Notarized Developer ID` is the result that matters —
the same sentence as last time, now with a build step behind it.

The extra step cost **25 seconds** in this build. An earlier estimate in this
note said "about an hour"; that was wrong — it generalised from v3.6.3, where
Apple's queue held the application for 64 minutes. In this build the
application took 26 seconds and the installer 24. Apple's turnaround varies
with their queue and is not a property of the added step; the whole macOS job
ran in 5m 24s.

Linux and Windows builds are untouched.

## Also settled since v3.6.3

**The menu-bar icon works, and its disappearance was never this app's doing.**
Studio creates the status item and asks for it to be shown; macOS 26 gives
third-party menu-bar items an *ephemeral* slot and simply drops them when the
bar is full — with no overflow menu and no setting to override it. On a notched
display that happens easily, and it hit Cursor, TeamViewer and Dropbox on the
same machine. Freeing space brings the icon back. No code change was needed.
