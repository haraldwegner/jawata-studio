# jawata-studio v3.10.0

The resident's credential leaves the command line, and the stop gate stops
holding your own conversation.

## Your token was readable by every process on the machine

Studio launched each resident with `-token <secret>` on its command line. Any
local process can read another's arguments — on Linux `/proc/<pid>/cmdline` is
world-readable — and on 2026-08-17 a coding agent that could not reach its MCP
tools did exactly that: it ran `ps aux`, read both residents' URLs and bearer
tokens, and started calling the endpoints directly.

Studio now writes the token into `<workspace>/resident.token` with owner-only
permissions and points the resident at the file. Nothing sensitive appears in
`ps`. Two details that matter:

- **The workspace log no longer holds the secret either.** The resident's READY
  line used to print the token, and Studio teed that line verbatim into a log
  file that outlives the process. Studio now redacts it on the way to the log —
  which also protects you when the resident is an older build that still prints
  it.
- **An older engine keeps the old channel, deliberately.** Reading the token
  from a file needs jawata-mcp **3.10.0** or newer. Given only a file, an older
  engine would generate its own token and every client Studio had just
  configured would fail with 401 and no explanation. So Studio checks the
  engine's version and uses the file only where it is read. Update the runtime
  to 3.10.0 to get the fix.

`hook_config.json`, which also carries the token, is now created owner-only.

Client configuration files are unchanged and out of scope: that is the
credential reaching the client that is supposed to have it, in your own home
directory.

## The stop gate no longer treats an answer to your question as a request

Ask a question, and the reply frequently ends on a clarifying line or quotes
your own words back — which the gate read as the agent asking YOU for a
decision. It then blocked the turn until a communicator subagent had judged a
message that, by the standing rule, was never in scope: replies to your own
questions are direct.

The gate now knows who asked first. If your message opened the turn with a
question — or an imperative like "Discuss!", "Explain", "Tell me" — the ask
check stands down. The length check does not: a wall of text is noise whoever
asked for it. An ask the agent raises on its own still blocks, unjudged, exactly
as before.

## The `.java` write guard explains its one rough edge

The guard blocks shell-mediated writes to Java files, and it deliberately
refuses a command that merely *mentions* a `.java` path from an interpreter,
because whether an opaque script writes the path it prints cannot be read off
the command text. A narrower version of that check was tried and reopened three
ways around the guard.

The refusal now says so, and names both routes that work: use the editing tool
for the non-Java file, or declare an authoring reason. The rough edge is
documented rather than removed — removing it needs a real shell parser.
