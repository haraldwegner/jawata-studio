# jawata-studio v3.7.13

No hook is registered that the client cannot run.

Claude Code's after-tool observer is still a shell script, on purpose: its
binary is a stub, and switching would lose tool-outcome capture and the
jawata-fallback record. That trade-off was weighed on Linux and macOS only. On
Windows a `.sh` cannot execute — the client launches it, it waits for input that
never arrives, and a console window sits on your screen **after every tool
call**.

So the choice was never "outcome capture or not". It was "lose outcome capture"
against "lose outcome capture *and* interrupt the user". The deploy now registers
a hook only where it can actually run, and **removes** an entry that cannot —
so an install already carrying one is repaired rather than left with it.

On Windows, Claude Code therefore has no after-tool observer until that binary is
finished. Everything else — the guard, the session primer, prompt recall, the
stop gate — runs as a native binary and is unaffected.

This is the same rule v3.7.12 applied to the deploy, now applied to registration.
The predicate takes the platform as a value rather than reading the host, so the
Windows answer is checked by a test on any machine — the specific blindness that
let a Windows-only defect survive five releases.
