# jawata-studio v4.5.1

**The studio now sets VS Code up by itself and starts the right jawata workspace for the folder an editor opens. The Workflow view shows where each seat sits.**

4.5.0 was tagged and never published: its two Windows builds stopped before any test ran, because the unit-test program of the crate could not start there (a test-only dependency needs a Windows manifest it does not carry), and its macOS build was cancelled by the runner before it began. 4.5.1 is the same change with the test-only dependency and the one test that uses it left out of Windows builds; that test runs on Linux and macOS.

## What you see

- **"Deploy to agents" covers VS Code completely.** One VS Code entry installs the two extensions (jawata chat and jawata Java), writes their settings, and uninstalls the competing Java extension (`redhat.java`). "Remove from agents" takes out what the deploy wrote; the competing extension is not put back. It needs the `code` command on PATH, and a `code` that lives inside a Cursor folder is refused. If the extensions cannot be installed, the deploy line says why instead of only counting.
- **An editor starts the studio for you.** With the extensions installed, VS Code starts the studio in the tray, with no window, when the engine's service does not answer, and waits until it does.
- **The folder VS Code opens decides which jawata workspace runs.** A jawata workspace that contains the folder is started if it was stopped, with no window. If no jawata workspace matches at all, the studio makes one from the folder and starts it, with no window. If a workspace matches only part of the folder, the studio opens its window and asks whether to add what is missing; nothing is changed until you answer.
- **The Workflow view shows every seat's place.** Seats outside the engine's tree (observer, report, review, rottenmeier, worker) used to show two empty fields; each now says why it has no place and what starts it. Choosing a parent and a role puts a seat in the tree; the choice is written into the deployed seat file and refused, with the engine's reasons, when the engine would refuse it.
- **The Memory view works without a workspace.** It no longer says "No workspaces, or their services are not reachable" beside "workspace starting, retrying automatically" when no workspace exists.
- **"Deploy to agents" is no longer left greyed.** The action has a time budget and always releases its busy flag.
- **Each of the eleven seats names its typed command** (`/refactor`, `/cover`, and so on), and the five hired helpers have one too.
- **Agent settings come from what is installed.** Every engine the studio starts gets the main brain, the hired brains and the reviewer written from the agent program found on PATH. Nothing is written for a program that is not installed, and no credential is ever written.

## How it works

- The extensions call the studio with `--background` and one `--editor-folder <path>` per folder. The studio answers through a small file in its configuration folder, `editor-workspaces/<id>.json`, which says `ready` only once the workspace's engine answers.
- The settings of Zed and the chat are edited in place: comments, order and whitespace stay, only the studio's own entry changes. A file that does not parse is refused with its line and column.
- The studio's list of engine tools is checked against the published engine; it now matches engine 4.5.2 (`plan_board` and `plan_steps` are new).
- Before a context compaction the stop hook stores any unsaved part of the discussion and holds the compaction until the agent has written a story list.

## Known limits

- Tried on Linux here, on the release build in a fresh home: the engine installed itself, all seven views opened, "Deploy to agents" installed both extensions from the published release, VS Code started on a folder with the studio closed and the extension started the studio with no window, and "Go to definition" in a Java file was answered through the studio's workspace. Not tried by hand on Windows or macOS; the Windows and macOS builds are checked by the release job.
- VS Code keeps extensions off in a folder you have not trusted; trust the folder once and the extensions start.
- The chat sends your message to the agent program installed on the machine; that program has to be signed in. A model's answer was not seen in the trial, because no program there was signed in.
- Only VS Code is covered; Cursor is left alone on purpose.
- Which seat the Workflow view shows as parent is the engine's signed tree; the studio does not change that tree, it only records your choice for seats outside it.

Works with jawata-mcp 4.5.2.
