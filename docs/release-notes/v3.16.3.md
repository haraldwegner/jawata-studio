# v3.16.3 — a false positive was disabling the autocontinue push

Third fix in the same family, and the one that explains the symptom the first two
did not: a session that stops **mid-task**, with nothing running, having just said
what it was about to do next. Reported as *"you are in the middle of nowhere and
just stop — this is even worse than with a hard cut at a checkpoint."*

## What was happening

The gate's own log tells it: `emitted, emitted, stop-allowed, stop-allowed`, where
the last released a turn that ended on a plan with no job armed. Both preconditions
for the push were satisfied — the grant was live, and the "did this turn arm work?"
check is correctly narrow (an agent spawn or a backgrounded command; a file edit
does not count).

The anti-loop valve sits at the **top** of the decision function and returns *allow*
before the push rule is ever reached. So the chain was:

1. A message trips the ask detector — often **falsely**, because the phrase list
   matched the bare substring `DECISION` inside ordinary prose like *"two design
   decisions"*.
2. The turn is bounced for review.
3. The agent rewrites without the trigger word, and the retry hits the valve, which
   releases it **before the push rule can look at it**.

So a false positive did not cost one bounce — it **disabled the push for that whole
turn**. And it fired hardest while the agent was discussing design, which is when it
is deepest in a task and least able to afford being stranded.

## The fix, in three parts

- **The push rule is excluded from the anti-loop valve.** It never needed that
  protection, because it carries its own ceiling.
- **The ask detector is word-bounded.** "decision", "decide", "ruling" and
  "approval" now match as words, and only where the sentence addresses the reader:
  *your decision* and *I need a decision* are asks; *makes no decision* and *design
  decisions* are descriptions. A message opening with `DECISION:` is still always an
  ask, whatever else it contains.
- **The ceiling counts what the rule is about.** It counted turns with *no tool calls
  at all*, while the rule fires on turns that *armed nothing* — different sets, and
  the stranding sat exactly in the gap: a turn that edits files and starts no job has
  tool calls, so it reset the counter and the ceiling never advanced. Without this,
  the first change would have traded a stranding for an unbounded block.

## Verification

Four regression tests named for the incident: a retry that armed nothing is still
pushed; a retry that did arm work is still released; four sentences that tripped the
detector live are no longer asks; five real asks still are. The last pair is asserted
together because either half alone passes for the wrong reason — a detector that
never fires satisfies the first, and the shipped one satisfied the second.

One existing test changed its fixture, declared rather than quietly adjusted: the
anti-loop wire test proves the retry flag is actually read by making two passes
disagree, and it disagreed via the push rule, which is now excluded. It now
disagrees via the length budget instead — a rule the valve still covers. The guard's
purpose is unchanged; only the rule carrying it moved.

Full hook suite: 20 suites, zero failures.
