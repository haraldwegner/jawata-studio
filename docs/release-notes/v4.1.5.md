# v4.1.5 — the full suite runs at checkpoints and releases, and the guard enforces it

One hook rule, on Harald's ruling of 2026-09-08. No other behaviour changes, and
nothing from Sprint 28e rides along: this release is built from the v4.1.4 tag
with the hook change alone, so the five commits that had landed on `main` since
that tag are deliberately absent.

## What was wrong

An agent decides for itself how often to run the whole test suite, and it always
decides too often.

Measured on Sprint 28e's first night — the sprint opened 2026-09-07 17:09 and by
08:05 the next morning had run the full suite **17 times: mean 11m20s, 3¼ hours,
a quarter of a 14-hour sprint.** About 13 of those bought nothing that the next
checkpoint would not have proved once. Four stages holding 34 issues were still
untouched at that point; on the same cadence they would have cost roughly 34
more runs.

Asked to state its own rule, the agent proposed *"run the full suite when a
change touches production code that something outside its own tests reads."*
Nothing is production until a release, so that clause is true of every edit and
discriminates nothing. Asked to self-govern here, it produced a test that always
says yes.

## Why it is a hook and not seat text

The sprint seat already contains the reason, in its check 9: a full suite
*"costs the agent nothing — it sleeps through the wall-clock — while every minute
lands on the person waiting."* That asymmetry was written down to argue for
defaulting diligence ON. It argues just as directly that an agent will over-run
the suite, because it is the one participant that cannot feel the price.

The seat's own layer rule then decides where the fix goes: *"a fix is GENERAL
only in a BINDING layer. The experience store carries knowledge and is a recall
nominee. Skill text binds the agent that reads it. Only a hook enforces."*
Applied here, skill text fails on a technicality that matters — `/sprint` is
invoked by the agent WRITING a spec or a plan, and an agent EXECUTING one never
invokes it. A rule placed there fires only when a session happens to have loaded
it.

## What changed

`jawata-hook-guard` gains a third gate, beside the two Java declarations. A
command that runs the WHOLE suite is refused unless it carries its reason:

    checkpoint: C4
    release: v4.2.0

Between checkpoints, run the touched classes and their siblings plus whatever a
mutation needs — none of that is affected.

Two shapes are recognised, both in COMMAND POSITION so that naming a runner in
prose does not fire:

- a project's own suite script (`run-suite.sh` and the common spellings);
- a build tool reaching a test phase with nothing narrowing it — `mvn verify`,
  `./gradlew test`. A run carrying `-Dtest=`, `-Dit.test=` or `--tests` is a
  selection and passes untouched, and so does `-DskipTests`, which is the build
  step that PRECEDES every legitimate suite run.

The gate runs BEFORE the Java declarations, deliberately: `jawata-author:`
short-circuits to allow, so placed after it an unrelated authoring window would
have bought a free full run — the same lattice defect v3.8.1 shipped one gate
over.

**It never prompts the user.** A hook that asks converts the agent's cadence
problem into the human's interruptions.

## What this does not claim

The declaration is SELF-CERTIFIED. Nothing stops an agent typing
`checkpoint: C4` on a run that is not one, exactly as nothing stops a weak
`jawata-fallback:` reason. The value is not the block — it is that N runs become
N logged claims, so a stage with four declared checkpoints and one real one is
visible in the observer's log afterwards. It converts an invisible habit into a
countable one.

If self-certification proves too weak in the field, the recorded fallback is a
blunt bound — refuse a second run with no intervening commit — which cannot be
gamed and will also refuse a legitimate re-run after a red suite. Not chosen now.

The requirement and its field measure are filed in Sprint 28f
(`sprint-28f-seats-lane-b.md`): over one sprint after this release, the count of
full-suite runs, and how many declared reasons a reader can match to a real
checkpoint or release.

## Verification

`cargo test` over the hook crate: **291 passed, 0 failed**, up from 283 — the
eight new cases are the gate's own.

One of them earned its place immediately. `merely_naming_the_runner_in_prose_does_not_fire`
went red on its first run: the first implementation scanned every word of a
segment, so `echo 'remember to run run-suite.sh'` was a denial. Command position
is this file's standing discipline — stated for the write gate as
`echo 'python Foo.java'` must not fire — and the gate had not followed it.
