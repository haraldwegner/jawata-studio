# v3.17.0 — the Memory tab stops hammering a store that cannot answer

Companion to jawata-mcp v3.17.1, which carries the actual cure. This release is the
client half plus two seat corrections.

## The incident, from this side

The Memory tab shows one thing about the store: reachable, or not. It learns that by
calling `experience(kind=stats)` with a five-second timeout and keeping the boolean.

In mcp v3.17.0 one part of that call scanned the substrate root — which on a real
machine derives to the user's home directory — so it never answered inside five
seconds. The client abandoned each request and retried on a fixed five-second timer,
but abandoning an HTTP request does not cancel the work behind it. Every retry left
another scan running. Measured on 2026-08-29: sixty-four concurrent home-directory
scans per resident, all twenty cores at 100%, load average 114, for as long as that
tab stayed open. The "Store unreachable" banner was generating the load that produced
it.

## What changed here

**The unreachable-retry backs off** — 5 s, then 10, 20, 40, capped at 60, reset the
moment anything answers. This is hygiene, not the fix: a throttle can only slow how
fast expensive work *arrives*, never subtract a job already running. It is shipped
because a client should not hammer an unresponsive server regardless of why the server
is slow. **The cure is mcp v3.17.1**, where the scan is gone and `stats` answers in
milliseconds.

## Seat changes

**The architect seat gains D-SIX — refuse a second implementation of a job the system
already does.** Before accepting a new source, reader, writer, importer or exporter,
the seat asks whether the system already does that job for other material; if it does,
the design that adds a second pipeline is refused and the material is re-authored into
the existing form. The rule names the failure shape, because it never arrives
announcing itself: the new material is not claimed to *behave* differently, only to
*feel* different — narrower, simpler, ours rather than theirs — so it gets its own
shape, the shape forces its own reader, and the reader becomes its own lifecycle.
Nobody chooses the second lifecycle; they choose the format, and the rest follows.

It also refuses the reflex cure. Extracting the shared lifecycle into a helper both
call is not the fix — a step a source *can* decline is a step a source *will* decline.
Two exceptions must be named or the design is refused: the lanes genuinely behave
differently (untrusted input needing quarantine or rate-limiting beside curated
input), or the second format is not yours to re-author (a vendor feed).

## Deployed text corrected for the current engine

`/memorize` and the review seat both said a direct `experience(kind=record)` is
removed by the next reseed. Since mcp v3.17.0 that is no longer true — the reseed
keeps it. The claim is now accurate and still reaches the same conclusion: such a row
has no file behind it, so **nothing can ever rebuild it**, and a bare wipe or a lost
store file takes it permanently. The test to apply is unchanged: after the next wipe,
what puts this back?
