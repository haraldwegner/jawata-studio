# v3.17.2 — the gate stops guessing whether you are there

**Any message you type ends the autocontinue grant. Only the word restores it.**
Nothing about your text is classified any more.

## What was wrong

The stop gate decides whether to push the agent onward, and to decide it needs one
fact: are you at the machine, or away? It has been answering that by reading your
words — and that answer failed in both directions inside four days.

- **You were there, it said absent.** The agent worked straight through a discussion
  you were having with it, and you had to interrupt twice.
- **You were away, it said present.** On 2026-08-29 at 22:54 the agent finished a
  piece of work, wrote *"Continuing to S9a.2"*, and slept until morning. The grant
  was on; nothing was armed; Rule B's own two facts were both true. It stood down
  because your 22:43 message — *"We had a discussion before … Move on with the plan
  and autocontinue"* — contained the letters `DISCUSS`, and a substring list read
  that as you asking a question.

Four releases had already narrowed that guess. `v3.14.2` introduced it. `v3.16.1`
fixed the channel it read from. `v3.16.3` fixed `DECISION` matching inside "design
decisions". `v3.17.1` stopped the agent revoking the grant on its own. Every one
improved the guess. None removed it.

## The two defects underneath

**The fact was computed once and never recomputed.** `user_asked` was set when your
message opened a window and then persisted for that whole window. At 22:54 the gate
asked *"is he here?"* and answered with a fact about 22:43 — eleven minutes and
forty-nine tool calls earlier. Even a perfect question detector fails identically:
ask something and walk away, and it correctly answers "he asked" and correctly sleeps
the night.

**And Rule B's condition existed twice.** Once as the rule, once as a copy named
`rule_b_would_push` inside the anti-loop valve. `v3.16.3` stopped that valve
swallowing Rule B by exempting it — but the copy carried the same stale flag, so the
exemption switched itself off in exactly the cases it was written for. It only ever
protected Rule B where Rule B would have fired anyway.

## The change

The grant is now a state with two edges, both on channels that carry real events:

| Event | Effect |
|---|---|
| A message of yours containing **autocontinue** | grant ON, counters reset — a fresh stretch |
| **Any other message you type** | grant OFF |
| **Esc / interrupt** | grant OFF (unchanged) |
| Anything the agent writes | no effect (unchanged — `v3.17.1`) |
| A harness notification | no effect (unchanged — `v3.16.1`) |

`user_asked` no longer reaches Rule B or its duplicate in the valve. The stop gate
reads none of your text.

**This also gives Cursor an off switch it never had.** Revoking was reachable only
from an Esc marker in the transcript, and Cursor has no Esc — it has a stop button
that writes no marker. So on that client the grant could be turned on and never off.
Your typing reaches every client.

## What still holds

studio#33 — *"there is a loop that bounces you back to work all the time, even if I
just ask a question"* — holds unchanged, and now for a reason the gate can observe:
your question ends the grant on arrival, so Rule B finds no grant. The test carries
its control, so a green cannot mean the push was simply disabled: after your word,
the very same turn is pushed again.

## Known cost

Saying "autocontinue" is now required each time you leave, including after a message
you meant as a passing remark. That is the deliberate trade: over-stopping costs you
one word, and under-stopping cost a night twice this week.

## Verified

`cargo test -p jawata-hook` — 266 unit tests and every integration suite green,
including the two shapes from 2026-08-29: your 22:43 message re-arming while naming a
past discussion, and the 22:54 turn that must now be pushed.
