# jawata-studio v4.3.3

**The memory store is reloaded from its story folder whenever an engine starts, and studio keeps a
log.**

## What went wrong

- **A restart did not reload the store.** Only Deploy, and adding, renaming or deleting a
  workspace, asked the engines to read the story folder again. So after an engine update the store
  stayed as the old version had written it. Found on a real store after 4.3.1: 55 heading rows that
  4.3.1 no longer produces were still there after the restart.
- **Deploy's reload never actually ran.** It read the engine's reply in the wrong format, never
  found the story folder, and skipped every time. It also gave up after ten seconds.
- **Studio's own messages went nowhere.** Started from the desktop, studio's output was thrown away,
  so a reload that was skipped or failed left no trace.

## What changes

- **Every engine that comes up reloads its store** — when studio starts it, restarts it after an
  update, or finds it still running after studio itself restarted. Deploy reloads too, now for real.
- **One reload per store per engine version.** Several engines sharing one store do not each load
  the same folder again.
- **The reload waits for the engine's answer** on its own thread and writes one line saying what
  happened: how many story files were written and how many notes are still waiting for their
  meaning vector.
- **Studio writes its log to `studio.log`**, next to the engines' logs in studio's logs folder. A
  studio started from a terminal keeps printing to the terminal.

The reload setting in studio's settings still switches all of this off. Works with jawata-mcp 4.3.0
and later; with 4.3.2 a reload no longer holds the engine for minutes.
