# jawata-studio v3.13.0

Two things the pattern-corpus import taught us, both found by using the product
in anger on a 194-module workspace.

## Residents no longer launch unbounded

Every workspace's resident started with no heap ceiling at all, so each one
inherited the JVM's ergonomic default — a quarter of physical RAM. On a 62 GB
machine that is **16 GB per resident**, and three residents were legally
entitled to 48 GB of it. Two long-running ones were sitting at about 8 GB each.

That 8 GB was not a leak, and this release does not treat it as one. Forcing a
full collection on those same two residents left **0.30 GB and 0.53 GB actually
live**; the 194-project pattern corpus settles at 0.33 GB live. What they were
holding was uncollected garbage — an unbounded heap is simply never asked to
give anything back, so it doesn't.

So: **every workspace now gets a heap ceiling, defaulting to 2048 MB** — a
number taken from those measurements rather than from taste, with room for the
garbage a generational collector is supposed to keep around. Settings gains a
**Workspace Memory** card with one box per workspace; leave a box empty to take
the default. Clearing a box returns the workspace to the default, never to
unbounded — that state is deliberately unreachable from the UI now. A ceiling
below 256 MB is refused with the number that would work, because a JVM too
small to hold a JDT workspace dies at spawn with a stack trace instead.

The setting applies at that workspace's **next start**, and the card says so: a
JVM's heap ceiling is fixed when the process launches, and bouncing a resident
out from under a working agent would be worse than a stale number.

## Importing a large project no longer freezes the window

Registering the 194-module corpus locked the window for 15–30 seconds with
nothing on screen. Two independent faults produced that one symptom, and fixing
either alone would have left it half-broken.

**The window really was frozen.** Tauri dispatches a synchronous command on the
main thread, and all three project-scanning commands were synchronous. While a
filesystem walk of that size ran, the window could not repaint or respond — so
no amount of progress reporting would have helped, because the progress could
not have been painted either. The three commands are asynchronous now.

**And there was nothing to paint.** Folder scanning already had a busy flag and
a "Scanning…" label. Discovering from a `.code-workspace` had neither: its
enablement rule never mentioned a busy state because no such state existed. For
the whole half-minute the button stayed live, still reading "Discover", and a
second click started a second walk. It now disables itself, reads
"Discovering…", says what it is doing within the first frame, and reports how
many projects it found.

## Verification

696 tests across 22 binaries, 0 failures; type check and production build clean.

Both fixes ship with controls rather than assertions: delete the heap-ceiling
line and four named tests go red, including one that exists only to catch an
`-Xmx` placed after `-jar`, where the JVM never sees it and the flag is handed
to jawata as a nonsense argument — the same bug wearing a fix's costume. Make
one scanning command synchronous again and the threading guard goes red with
the reason.

Closes `studio#27` and `studio#28`.
