# v3.17.4 — while you are talking, the agent may not turn around and work

**Two fixes to the same mechanism, one of which was mine from this morning.**

## 1. The push no longer runs forever

v3.17.3 shipped a limit that could not be reached. The rule that pushes the agent
onward fires when a turn started nothing that will wake the session later. The
limit meant to stop that pushing forever counted something different — whether
the turn *accomplished* anything. On the most ordinary turn there is (edits, no
background job) those disagree: the rule fires, the limit resets, and the pushing
never stops.

Measured in v3.17.3's own log the evening it shipped — six consecutive blocks,
the counter reading zero on every one.

**The fix is not a bigger limit.** A push that produces real work is the
mechanism succeeding, and capping that caps the feature. The only loop worth
stopping is push → nothing → push → nothing, which costs money and produces no
output. So:

| | asks | decides |
|---|---|---|
| the rule | will anything wake this session? | whether to push |
| the limit | did this turn produce anything? | when to stop pushing |

This also dissolves the "two-turn leash": an unattended editing run is no longer
let go after two turns of real work. Only two turns of producing nothing end it.

I reverted this twice before getting it right, and the reasoning is left in the
code rather than tidied away — the first revert was sound about a limit on
*blocks* and I applied it to a limit on *emptiness*.

## 2. Answering you is no longer a launch pad

**Harald, 2026-08-30:** *"in a conversation is the other way round. You are not
working on a plan but talking with me -> Hence, don't turn around and work on
something."*

Measured the same evening: four questions in a row, each answered and then used
as the opening of an unrelated task. At 23:01:44 a commit landed in the
repository mid-question — while the gate's own record for that window already
read "he is present". The signal existed and nothing consulted it.

**What now happens.** When your own message opened the current turn, and the
agent has already emitted a substantial answer inside it, a change is refused
before it happens. The refusal says what to do instead: make the change first and
let the answer be last.

**Reads are never refused.** Answering you often requires them.

**It is a refusal, not a report.** The stop gate runs when the turn is over — it
could have recorded that commit but never prevented it. A control that must stop
something, built on a channel that only runs afterwards, is the shape this
project's own architecture rules refuse. So this one sits before the call.

### The part that is a guess, said plainly

Separating "a complete answer" from "narration between two tool calls" has no
clean signal: they are the same kind of thing and differ only in length. The cut
is **600 characters**, chosen from that evening's transcript — narration ran
100–400, answers to questions 700–2400 — and it sits in the gap. That is the most
that can honestly be claimed for it.

The failure direction is deliberate. Over-firing costs one reorder, which is the
shape the rule wants anyway. Under-firing costs what happened that night.

## Four controls, because a rule that refuses everything is not a rule

Each runs the real binary, not the decision function:

- a **read** after an answer is allowed
- **short narration** is not an answer, so ordinary working turns are untouched
- a window opened by a **background job finishing** does not freeze the work —
  that would re-create the defect v3.17.3 fixed on the other side of this gate
- an **unreadable transcript** refuses nothing; a guard that blocks when it
  cannot see is worse than the fault it prevents

The first draft of those controls passed **vacuously** — they asserted the
absence of a key that never appears in the client dialect under test, so they
would have agreed with any behaviour at all. They now assert the allow verdict
positively, and both dialects are matched.
