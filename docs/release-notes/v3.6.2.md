# JAWATA Studio v3.6.2

**Studio froze on start-up and when stopping the services.** A blank window, and
the system offering to force-quit it. This release fixes that, and the design
error behind it.

## What was happening

Reading the dashboard — simply asking Studio what its current state is — went
out to the network, and, if the update policy said to install, downloaded and
unpacked the 112 MB runtime **before returning**. That work ran on the thread
that draws the window, so the window could not be drawn until it finished.

Nine operations end by reading the dashboard: start all, stop all, reload,
adding or deleting a project, saving settings, deploying. So **pressing Stop
fetched a runtime.** And because each of those reads could start its own
transfer, several ran at once — three concurrent downloads inside two minutes,
on the machine where this was found.

v3.6.1 made it visible by changing the default to install updates rather than
ask. The download was the trigger; the fault was that a read was doing the
downloading, on the thread that has to stay free.

## What changed

Reading the dashboard now answers from what Studio already knows. It performs
no network call and installs nothing.

Checking for a new runtime — and installing it, if that is the policy — happens
in the background, starting a few seconds after launch, and **only one such
check runs at a time**. When it finds something new, the window updates itself.
Saving settings behaves the same way: it returns at once, and any re-check runs
behind it.

Automatic updates stay switched on by default. They can no longer make the
window stop responding.

## Verification

243 tests pass, 0 fail.

**Stated plainly: the fix was released without first running the built
application.** It was made and shipped while Studio was unusable, on the
author's instruction to release immediately. What is verified is that it
compiles and that the whole suite passes; what is not verified is the
behaviour on a running app, which is the thing that broke. If a launch or a
stop still hangs, that is the finding, and the underlying cause — a read
performing network work on the UI thread — is now documented in the code at
`ManagerService::load_dashboard`.
