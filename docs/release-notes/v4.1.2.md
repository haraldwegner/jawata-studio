# v4.1.2 — a subagent's window is not his window

Found by dogfooding v4.1.1 in anger: the architect seat was run in fresh context
over a real run of fixes, and it could not run its own gates. Its report says so
in its first table — `compile_workspace` and the Rust suite **NOT RUN, therefore
NOT passed**. Every shell call it made was refused by our own turn-around guard.

## What was wrong

The turn-around guard exists for one sentence of Harald's, 2026-08-30: *"You are
not working on a plan but talking with me -> Hence, don't turn around and work on
something."* Its premise is that **he opened this window and is waiting to read
the answer.**

In a subagent that premise is false. The window is opened by the parent agent's
prompt, and he is not reading any of it. The harness marks this — every line of a
sidechain carries `"isSidechain": true` — and nothing in the hook binary read that
field.

**The one-shot reset could not end it either, and that is the part worth
keeping.** v3.17.6 made the refusal fire once per window: the denial comes back
as a tool result carrying `ANSWER FIRST OR WORK FIRST`, and seeing it clears
`answered_substantially`, so the next attempt proceeds. That works in his
session, where his next message ends the window. In a sidechain there is no such
message — the subagent writes its next paragraph, the flag is set again, and the
next call is refused. The speed bump is a wall.

Measured on the seat's own transcript: **six refusals in one sidechain**, every
one on a read-only shell command, the denials arriving in exactly the shape the
reset looks for. So the reset fired each time and was undone each time.

## Why the fix is the premise and not the reset

v3.17.5 built the rule. v3.17.6 made it one-shot after it deadlocked a dispatch.
A third repair on the reset — making it sticky, counting it, timing it out —
would have been the third face of one structure, each fix breaking something
different from the last. That is the alarm rule 12 shipped for yesterday, applied
to our own work.

So `Turn` gains `sidechain`, read per LINE rather than per file — a main-session
transcript can carry sidechain lines too, and a substring test over the tail
would disable the rule in the session he *is* typing in, which is the wrong
direction for a guard to fail in. The turn-around guard returns early when the
window is a sidechain. `human_window` is deliberately untouched, so the stop
gate's own use of it is unchanged.

A seat that cannot verify is this product breaking its own discipline, which is a
worse outcome than any commit this rule prevents.

## Also: rule 12 described the gate it points at as it behaved before 2026-09-01

Shipped yesterday in v4.1.1, and wrong on the day it shipped. The rule said the
mechanical half refuses *"a patch release with any other release inside seven
days"*. The patch-streak gate stopped counting that way on 2026-09-01 — its own
comment says why: the broad predicate refused v4.0.1 over ten neighbours that
were four feature releases on four different minors, no streak at all. It now
counts other patches on the same major.minor.

The proposal the rule was applied from verbatim predates that change, so the rule
about not trusting a stale note shipped carrying one. Corrected, and measured
rather than reasoned:

| tag | what the gate actually sees |
|---|---|
| `v3.17.2` | STREAK, 1 neighbour (`v3.17.1`) — the tail of that run |
| `v3.16.1` | OK, nothing — the head of the **same** run is invisible to it |
| `v3.7.16` | 7 neighbours, all `v3.7.x` — fully caught |

So the rule's own second example is a run the gate sees only in part. The text now
says PARTLY, names the real predicate, and says which of its own examples the
mechanism misses.
