# jawata-studio v3.7.3

The deploy stops overwriting its own hook programs.

v3.7.2 wired the client to the new hook binaries — and its deploy then wrote
four of the old shell scripts back over four of them, under the same
filenames, so every file looked deployed while four of six events ran the
previous generation. Found by the dogfood of the installed release; the
per-step checks all passed at their own instant, only the end state was wrong.

What this release changes, concretely:

- **A full deploy now ends with the five live role binaries actually invoked**
  — the binaries land first, and no writer in the codebase is able to put a
  script body over a hook binary's path anymore. A regression test runs the
  whole deploy sequence and fails if the overwrite ever comes back.
- **Memory recall on file edits works.** Two independent breaks fixed: the cue
  reader treated every absolute file path as a typed slash command (on Linux
  all paths start with `/`), and the event filter never forwarded editor
  edits to the recall hook in the first place. Editing `Foo.java` now recalls
  the store's prior lessons for `Foo`.
- **The observer keeps its working generation.** Its binary replacement is a
  stub, so switching to it had silently stopped tool-outcome capture and the
  `jawata-fallback:` audit trail. Which generation is live is now declared per
  role in the shared contract, the deploy removes the stale observer binary,
  and the cutover is blocked until the replacement really covers the role.
- **The stop gate that runs is the full one** — all eight rules, and block
  reasons that state the actual trigger (v3.7.2's surviving script blamed
  every block on an unjudged decision ask, whatever the real reason).

The deploy self-checks now exercise the binaries directly, and each hook
answers the self-check through the same rendering path production uses.
