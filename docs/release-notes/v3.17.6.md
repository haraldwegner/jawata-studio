# v3.17.6 — the refusal fires once, then stands aside

**One fix, measured within an hour of v3.17.5 reaching this machine.**

## The deadlock

v3.17.5's turn-around rule refuses a change made after a substantial answer
while you are present. Its design claim was "over-firing costs a reorder". The
first real dispatch proved that wrong: a task whose own protocol requires the
answer *first* (a review list before the files it approves) tripped the
600-character bar, and every write for the rest of the window was refused — while
the only reset lived on a stop-gate push that cannot come with the grant off.
Mid-window, a reorder is impossible. The real cost was the window.

## The fix

**The refusal is one-shot per window.** The first attempt to turn an answer into
work is still refused, with the rule named — that interruption is the control,
and it is on the record. Once the guard's own denial appears in the transcript,
the retry proceeds. Repeating the refusal buys no compliance the first one did
not; it only builds the deadlock.

The denial text now says so, and the marker the stop-reader keys on is one
shared constant with the guard that emits it — two copies of one condition is
how three fixes this week went missing from one side.

One escape found during the fix, worth the note: the new transcript arm
initially swallowed the tool-result lines another rule reads (the degraded-answer
counter) — four unrelated tests went red at once, which is shadowing announcing
itself. Both jobs now live in the one arm, with the reason in place.

## Verified

`cargo test -p jawata-hook` — all 22 suites, exit 0, including the new
real-binary case: a window carrying the guard's own denial allows the retry,
while the first-refusal case stays refused. Build clean, zero warnings.
