# jawata-studio v3.7.10

The Windows hook deploy, fixed at the cause — and made testable.

**Install this over v3.7.9.** That release wrote Cursor's hook binaries under
names Windows cannot execute and left three bash hooks live. On a machine
upgrading from v3.7.8 the guard kept working only because the older version had
left a correctly-named file behind; on a clean install there was no working
guard at all.

## What was wrong

One function wrote the hook binaries and every other place read them, and they
disagreed about the filename. The writer produced `jawata-hook-guard`; every
reader looked for `jawata-hook-guard.exe`. Six lines above the writing loop, the
same function's cleanup loop used the correct name — one function, two
conventions.

On Linux the two spellings are identical, so nothing was visibly wrong. On
Windows the resolver never found what the deploy had just written, fell back to
the shell scripts, and those cannot run there.

## Why five releases shipped it

The filename convention was decided at compile time. A test could therefore only
ever exercise the convention of the machine running it — and on Linux, where the
work was done and where the tests run, both conventions produce the same string.
The defect was not merely untested; it was **unrepresentable in the test suite**.
470 passing tests could not have caught it, and did not. It was found by a human
reading a directory listing on a Windows 11 machine.

## What changed

The convention is now a value the code passes around rather than a compile-time
constant, so a test can ask for either one from any machine. Two new tests do:
one asserts that what the deploy writes is what the resolver looks for, the other
that after a deploy every Cursor hook entry names a file that actually exists and
none names a shell script. Both run for the Windows convention on Linux, and both
were confirmed to FAIL against the v3.7.9 code before the fix went in.

The filename is now spelled in exactly one place, and the writer asks for it
instead of assembling its own.

## And the silent part

The deploy treated "the binary is missing" and "this role is meant to run as a
script" as the same thing, so any failure quietly became a bash hook. That is a
real fallback on Linux and a fiction on Windows, where a `.sh` cannot execute.
The deploy now refuses on a platform with no working fallback, and says so,
rather than reporting success over a broken install.
