# v3.18.1 — the stagger moves off the thread that repaints the window

**v3.18.0 traded a CPU spike for a longer freeze.** The stagger it added to
`start_all_runtimes` — so three residents stop beginning cold imports in the same
second — was implemented as a blocking sleep between spawns, on a *synchronous*
Tauri command. Tauri runs those on the main thread. Three workspaces, two gaps,
ten seconds each: twenty seconds of "jawata does not respond" on every fleet
start.

That is the opposite of what the stagger is for. The thing being protected is the
machine feeling usable, and the fix made the window unusable for longer than the
spike ever did.

The command is now `async`, so it runs on the async runtime and the window stays
live while the spawns are spaced out. The stagger itself is unchanged — it was
right; the thread was wrong.

**This had already been fixed once, and written down.** studio#27 made three
commands async after a workspace walk froze the window for 15-30 s, and left the
rule two lines above the function v3.18.0 broke: *"Tauri runs a SYNCHRONOUS
command on the main thread."* The comment was a rule for whoever read it, and
whoever edited the function beneath it did not.

So the rule is now a test rather than a sentence. `ui_thread_is_not_a_sleeping_place`
asks two questions of every command on every run: does a synchronous command
sleep, and does a synchronous command call a method its own author marked
*"must never be called from the main thread"* — the marker `sync_releases_now`
has carried since v3.6.2 for a 112 MB download. `start_all_runtimes` now carries
it too.

Two things the test's own construction is worth knowing for:

- **Its first version would not have caught the regression it was written for.**
  It matched `sleep` inside command bodies, but the sleep lives one call away in
  `manager_service`. Reverting the fix proved it: the named test went red, the
  general one stayed green. Following the codebase's blocking marker across the
  file boundary is what closed that.
- **Its second version condemned correct code.** It immediately flagged
  `update_settings`, which calls the blocking method inside `std::thread::spawn`
  precisely to avoid this defect. A check that fails the code written to prevent
  the bug gets switched off, and takes its true positives with it — so the check
  is now spawn-aware, with a control proving both directions.

Tests: 763 passed, 0 failed.
